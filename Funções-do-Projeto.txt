DOCUMENTAÇÃO FUNCIONAL E TÉCNICA - WISHDIET
============================================

Objetivo
--------
Este documento descreve as telas, rotas, serviços, funções principais e fluxos
do projeto WishDiet/Wesh Diet. Ele foi elaborado com base na estrutura atual do
repositório e inclui o fluxo de autenticação, paciente, nutricionista,
administrador, IA, exames, evolução, planos alimentares e base TACO.

Data da documentação: 26/11/2026


1. VISÃO GERAL DA ARQUITETURA
==============================

Frontend
--------
- React Native com Expo SDK 54.
- Expo Router para navegação por arquivos.
- TypeScript.
- AsyncStorage para sessão local.
- apiFetch para comunicação HTTP com o backend.

Backend
-------
- Python com FastAPI.
- PostgreSQL acessado pelo driver psycopg.
- JWT para autenticação.
- OpenAI Responses API para geração estruturada.
- Pydantic para validação dos dados.
- Armazenamento privado para PDFs de exames.

Perfis de acesso
----------------
- Paciente: consulta seu perfil, exames, evolução e plano aprovado.
- Nutricionista: administra pacientes vinculados, exames, evolução e planos.
- Administrador: aprova nutricionistas e importações da base TACO.


2. NAVEGAÇÃO E PROTEÇÃO DE ROTAS
==================================

Arquivo: app/_layout.tsx

RootLayout
----------
Componente raiz da navegação. Instala o AuthProvider, seleciona o tema claro
ou escuro, configura a barra de status e registra as telas Stack.

RootNavigation
--------------
Guarda central de rotas. Verifica:
- se a sessão ainda está sendo restaurada;
- se existe token e usuário;
- se o usuário é administrador;
- se o usuário é paciente;
- se o usuário é nutricionista;
- se o acesso está tentando entrar em um grupo de perfil incorreto.

Regras principais:
- usuário sem sessão vai para /login;
- administrador fica na área /admin;
- paciente fica em /(paciente)/dashboard;
- nutricionista fica em /(nutricionista)/dashboard;
- grupos de paciente e nutricionista não podem ser acessados pelo perfil oposto.

AuthContext
-----------
Arquivo: contexts/AuthContext.tsx

AuthProvider
Gerencia a sessão global do aplicativo.

Responsabilidades:
- recuperar token e usuário do AsyncStorage;
- carregar a sessão local imediatamente;
- validar o token em /auth/me;
- aplicar timeout de 8 segundos na validação;
- manter a sessão local quando o backend está indisponível;
- limpar a sessão quando o backend rejeita explicitamente o token;
- registrar comportamento global para respostas HTTP 401.

useAuth
Hook usado pelas telas para acessar:
- usuario;
- token;
- isLoading;
- signIn;
- signOut.

signIn
Salva token e usuário no AsyncStorage e atualiza o estado global.

signOut
Remove token e usuário do AsyncStorage e limpa o estado global.


3. SERVIÇO HTTP DO FRONTEND
============================

Arquivo: services/api.ts

API_BASE_URL
Define o endereço da API. Usa EXPO_PUBLIC_API_URL ou um endereço padrão.

ApiError
Classe de erro com status HTTP e código opcional.

definirAoSessaoExpirar
Registra a função chamada quando uma requisição retorna 401.

apiFetch
Função HTTP centralizada.

Responsabilidades:
- recuperar token do AsyncStorage;
- enviar Authorization Bearer;
- definir Content-Type JSON quando necessário;
- serializar o body;
- converter resposta para JSON;
- normalizar mensagens de erro;
- disparar o encerramento da sessão em 401.

app/(tabs)/nutricionista/GeraPlanoAlimentar.tsx
------------------------------------------------
GeraPlanoAlimentar
Tela de criação, revisão e aprovação de planos alimentares.

Fluxo:
1. Lista pacientes vinculados.
2. Permite buscar paciente por nome.
3. Carrega o contexto clínico.
4. Mostra objetivo, restrições, peso, adesão e observações.
5. Solicita geração do plano.
6. Salva o resultado como rascunho.
7. Exibe refeições e substituições.
8. Permite editar o plano estruturado.
9. Permite solicitar revisão.
10. Permite aprovar e liberar para o paciente.

Rotas usadas:
- GET /nutricionista/planos/pacientes;
- GET /nutricionista/planos/pacientes/{id}/contexto;
- POST /nutricionista/planos/gerar;
- PATCH /nutricionista/planos/{id};
- POST /nutricionista/planos/{id}/revisao;
- POST /nutricionista/planos/{id}/aprovar.

Estados do plano:
- rascunho;
- revisao_solicitada;
- aprovado;
- arquivado.

Regras importantes:
- somente pacientes vinculados aparecem;
- consentimento de IA é exigido;
- o plano precisa ter duas substituições por refeição;
- o plano precisa de aprovação profissional;
- o paciente só visualiza o plano aprovado.

21. REGRAS DE NEGÓCIO IMPORTANTES
==================================

- Dados de saúde só podem ser acessados pelo paciente ou nutricionista vinculado.
- Nutricionista precisa estar aprovado para funções clínicas.
- Administrador controla aprovações administrativas e da base TACO.
- Consentimento do paciente é obrigatório para processamento por IA.
- IA gera propostas, não decisões clínicas definitivas.
- Plano nasce como rascunho.
- Plano precisa de duas substituições por refeição.
- Nutricionista deve revisar e aprovar.
- Paciente recebe somente plano aprovado.
- Relatório de exame só fica disponível após aprovação profissional.
- Base TACO importada fica pendente até aprovação.
- Versões antigas da TACO devem permanecer rastreáveis e podem ser inativadas.
- Valores TACO devem ser usados como dados estruturados do backend, não como texto
  integral enviado ao prompt.


22. LIMITAÇÕES ATUAIS IMPORTANTES
==================================

- A base TACO já foi importada, mas a importação ID 1 está pendente.
- O catálogo aprovado é enviado ao contexto da geração, mas os cálculos
  nutricionais determinísticos completos ainda precisam ser ampliados.
- A tela de edição do plano utiliza edição do conteúdo estruturado em JSON.
- A tela administrativa TACO é simples e não possui upload de arquivos; o importador
  é executado pelo backend/terminal.
- O fluxo de mensagens ainda é básico.
- Algumas telas possuem componentes legados/duplicados mantidos por compatibilidade.


23. FLUXOS PRINCIPAIS RESUMIDOS
================================

Login:
usuário informa credenciais → backend valida → JWT → sessão local → guarda de rotas.

Vínculo:
nutricionista fornece código → paciente informa código → backend cria vínculo ativo.

Evolução:
paciente envia check-in → backend calcula diferenças → IA ou fallback local →
histórico → nutricionista consulta.

Exame:
paciente envia PDF → backend valida arquivo e autorização → extrai texto →
IA gera relatório → nutricionista revisa → paciente visualiza se aprovado.

Plano:
nutricionista seleciona paciente → contexto clínico → catálogo TACO aprovado →
IA gera rascunho → nutricionista edita ou solicita revisão → aprova → paciente visualiza.

TACO:
CSV validado → importação pendente → administrador aprova → catálogo fica disponível
para consultas profissionais e contexto de geração.
